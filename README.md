# terraform-policy-agent Quick Start Guide

> **New here?** Follow **[USER_GUIDE.md](USER_GUIDE.md)** for a step-by-step walkthrough. This README is the technical quick-start reference.

## What it does

Terraform Policy Agent converts Sentinel and OPA (Rego) policies into Terraform Policy (TFPolicy) code. An AI coding agent running in a container, using the model provider you choose (GitHub Copilot, Amazon Bedrock or LiteLLM), reads your policies and, for each one, produces:

- a policy file (`*.policy.hcl`)
- a test file (`*.policytest.hcl`) and test fixtures
- a report describing how the policy was converted and any limitations

It also writes a summary across all policies.

## What it does not do

- It does not guarantee a correct or complete conversion. Output is LLM-generated: **review it and run `tfpolicy test` before using it** (see [Supported inputs and limits](#supported-inputs-and-limits)).
- It does not run without a model provider account or credentials.
- It does not upload your files anywhere except to the model provider you configure (see [Data and Privacy](#data-and-privacy)).

## Supported inputs and limits

**Policy languages**

| Input | File extension | Notes |
|---|---|---|
| Sentinel | `.sentinel` | Inline code, file paths in `policy_goal.txt`, or an external repository. Mock files (`test/<policy-name>/`) are used when present. |
| OPA / Rego | `.rego` | Used exactly like Sentinel: the input is the same, with `.rego` files instead of `.sentinel` files. In an external repository, `*_test.rego` files are skipped. A sample is in `sample-data/input/opa/`. |

**Cloud providers**

- **Tested:** AWS, Azure and Google Cloud (GCP).
- **Other providers:** any provider published in the Terraform Registry is supported, because the agent looks up provider schemas and documentation through the Terraform MCP server and validates against them. These other providers have not been tested as extensively, so review their output with extra care.

**Limits**

- Not every Sentinel or Rego construct has an equivalent in TFPolicy. When part of a policy cannot be converted, the agent records it as a **Policy Limitation** in the policy's `report.md` and in `summary.md`. Read these before relying on a converted policy.
- Each input file is converted to one policy. Policies that depend on external data sources, custom imports or functions outside the file may need manual follow-up.
- Conversion needs network access to your model provider and to the Terraform Registry (through the MCP server), and TFPolicy 0.3.0 or later for validation.
- Results depend on the model you choose and can differ between runs.

> **Review required:** the output is generated by a large language model. It can be incomplete or wrong. **Always review the generated policies and run `tfpolicy test` on them before using them.**

## Quick start

1. [Set up the workspace and prerequisites](#getting-started) (container runtime, image, Terraform and TFPolicy binaries, MCP server).
2. Copy `.env.example` to `.env` and [configure it](#3-configure-environment) (provider, credentials, binary paths).
3. Run the pre-flight check: `./pre-check.sh`
4. Put your Sentinel or OPA (`.rego`) policies and a `policy_goal.txt` in place, or set `EXTERNAL_REPO_DIR` (see [Usage](#usage)).
5. Run `./run.sh` and read the results in `data/output/summary.md`.

**Documentation:** [USER_GUIDE.md](USER_GUIDE.md) is the step-by-step walkthrough with screenshots and [TROUBLESHOOTING.md](TROUBLESHOOTING.md) lists known errors and fixes. The quickstart above does not depend on them.

Example of `summary.md`:

```
| Policy Name  | Status     | Policy Limitation | Total test cases | Passed | Failed |
|--------------|------------|-------------------|------------------|--------|--------|
| cloudfront-6 | ✅ Success | ⚠️ Yes            | 5                | 5      | 0      |
```

### 2. Prerequisites

**Python**:

Python 3.10 or later is required.

```bash
python3 --version  # Must be 3.10 or later
```

If Python is missing or outdated, install or update it.

**Container CLI Runtime**:

The agent runs in a container, so you'll need either `docker` or `podman` available on
your system.

**Container CLI**:

`docker` is the default container CLI (it is the default in `.env.example` and in the scripts). To use Podman
instead, set this in your `.env` (see [Container CLI](#container-cli) below):

```bash
DOCKER_CLI=podman
```

That single setting is all that is required — `run.sh`, `stop.sh`, `pre-check.sh` and the
build scripts all read it. **You do not need to alias `docker` to `podman` (or the reverse).**

The commands throughout this guide use `docker`. Replace `docker` with `podman` if that is what you
configured.

**Container Image**:

Pull the pre-built container image from Docker Hub
([hashicorp/terraform-policy-agent](https://hub.docker.com/r/hashicorp/terraform-policy-agent)).
No login is required:

```bash
docker pull docker.io/hashicorp/terraform-policy-agent:0.0.33
# or, with Podman
podman pull docker.io/hashicorp/terraform-policy-agent:0.0.33
```

The short form `hashicorp/terraform-policy-agent:0.0.33` also works with Podman and Docker, but the fully qualified `docker.io/...` name is used throughout this guide because it never triggers a registry-selection prompt on hosts without a configured default registry. The image is about 1.1 GB on disk, so keep at least 3 GB free.

**Required Binaries**:

Download the following **Linux** binaries (they are mounted into and run inside the container). The architecture must match the container image (Linux ARM64 for M1/M2/M3 Macs and ARM hosts, Linux AMD64 for Intel Macs and x86-64 Linux):

- **Terraform CLI**: https://releases.hashicorp.com/terraform
- **TFPolicy CLI**: https://releases.hashicorp.com/tfpolicy (version **0.3.0 or later**)

You may also use your own copies (for example from an internal mirror). Set `TERRAFORM_BINARY_PATH` and `TFPOLICY_BINARY_PATH` in `.env` to their paths. They must be executable Linux binaries matching the image architecture.

Manual install example (Linux AMD64; for ARM64 replace `amd64` with `arm64`):

```bash
mkdir -p bin
curl -fsSLo /tmp/terraform.zip https://releases.hashicorp.com/terraform/<TF_VERSION>/terraform_<TF_VERSION>_linux_amd64.zip
curl -fsSLo /tmp/tfpolicy.zip  https://releases.hashicorp.com/tfpolicy/<TFP_VERSION>/tfpolicy_<TFP_VERSION>_linux_amd64.zip
unzip -o /tmp/terraform.zip -d bin && unzip -o /tmp/tfpolicy.zip -d bin
chmod +x bin/terraform bin/tfpolicy
# then: TERRAFORM_BINARY_PATH=./bin/terraform  TFPOLICY_BINARY_PATH=./bin/tfpolicy
```

#### Required MCP Server

- **terraform-mcp-server**: HashiCorp's MCP server for Terraform operations
  - Must be running on `localhost:8500`
  - For detailed setup instructions, see: [terraform-mcp-server repository](https://github.com/hashicorp/terraform-mcp-server)
  
  **Recommended Setup:**
  
  Pull and run the MCP server:
  
  ```bash
  # Pull the MCP server image
  docker pull docker.io/hashicorp/terraform-mcp-server:1.1.0
  
  # Run the MCP server (use `podman` instead of `docker` if that is your CLI)
  docker run -d \
    --name terraform-mcp-server \
    -p 127.0.0.1:8500:8080 \
    -e TRANSPORT_MODE=streamable-http \
    -e TRANSPORT_HOST=0.0.0.0 \
    -e MCP_SESSION_MODE=stateless \
    --restart unless-stopped \
    docker.io/hashicorp/terraform-mcp-server:1.1.0
  ```
  
  The port is published on `127.0.0.1` only, so the MCP server is not reachable from other machines on your network. The agent container reaches it through `host.docker.internal`. This is verified on macOS with Podman. On Linux, if the pre-check cannot reach the server, check that `host.docker.internal` resolves inside the container (see `DOCKER_RUN_EXTRA_ARGS` under Container CLI); only if it still fails, publish the port as `-p 8500:8080` and restrict access with a host firewall.
  
  **Verify connectivity:**
  
  Using pre-flight check:
  ```bash
  # Check MCP server only
  ./pre-check.sh mcp
  ```
  
  Or using curl from the Terraform Policy Agent container:
  ```bash
  docker run --rm -it --entrypoint "" \
    docker.io/hashicorp/terraform-policy-agent:0.0.33 \
    curl http://host.docker.internal:8500/health
  ```
  
  Expected response:
  ```json
  {"status":"ok","service":"terraform-mcp-server","transport":"streamable-http","endpoint":"/mcp"}
  ```

#### Authentication Configuration

Choose one of the following authentication providers:

**Option A: GitHub Copilot (Default)**

```bash
AUTH_PROVIDER=github-copilot
MODEL_NAME=claude-sonnet-4.6
GITHUB_COPILOT_ACCESS_TOKEN=gho_your_access_token
GITHUB_COPILOT_REFRESH_TOKEN=gho_your_refresh_token  # Optional, defaults to access token
GITHUB_COPILOT_EXPIRES=0  # Optional, defaults to 0
```

- `AUTH_PROVIDER`: Set to `github-copilot`
- `MODEL_NAME`: A model your GitHub Copilot plan offers (for example `claude-sonnet-4.6` or `gpt-5.2`). See [Which model to use](#which-model-to-use). You can switch models without changing the access token
- `GITHUB_COPILOT_ACCESS_TOKEN`: Your GitHub Copilot access token
- `GITHUB_COPILOT_REFRESH_TOKEN`: (Optional) Refresh token, defaults to access token if not set
- `GITHUB_COPILOT_EXPIRES`: (Optional) Token expiration timestamp, defaults to 0

**Option B: LiteLLM**

```bash
AUTH_PROVIDER=litellm
MODEL_BASE_URL=https://your-litellm-endpoint.com
MODEL_NAME=<model-name-in-litellm>
MODEL_API_KEY=sk-your-litellm-api-key
```

- `AUTH_PROVIDER`: Set to `litellm`
- `MODEL_BASE_URL`: Your LiteLLM endpoint URL
- `MODEL_NAME`: The model name as configured in your LiteLLM endpoint
- `MODEL_API_KEY`: Your LiteLLM API key

**Option C: Amazon Bedrock (Bearer Token)**

```bash
AUTH_PROVIDER=amazon-bedrock
MODEL_NAME=anthropic.claude-opus-4-5-20251101-v1:0
MODEL_API_KEY=your-base64-encoded-bearer-token
```

- `AUTH_PROVIDER`: Set to `amazon-bedrock`
- `MODEL_NAME`: Bedrock model ID (e.g., `anthropic.claude-opus-4-5-20251101-v1:0`)
- `MODEL_API_KEY`: Your Bedrock Bearer Token (Base64 encoded API key)

#### Which model to use

There is no fixed list of supported models. Any recent, capable model works well: in testing, Claude Sonnet 4.6 and newer, the Claude Opus models and the current GPT models all gave good results. Older or smaller models are more likely to produce incomplete or incorrect policies, so run a small batch and review the output before converting a large set.

#### Container CLI

```bash
# docker (default) or podman
DOCKER_CLI=docker
```

Priority: this `.env` file > environment variable > default (`docker`, when `DOCKER_CLI` is not set anywhere).
To use Podman, set `DOCKER_CLI=podman`.

Only this one line is needed to switch between Podman and Docker; no alias is required.

**Windows**

Native Windows is not supported (the run scripts are bash). WSL 2 has not been tested.

**Podman on Linux**

Two host-specific flags may be needed. Pass them through with
`DOCKER_RUN_EXTRA_ARGS`, which is split with shell-style quoting (quote values that contain spaces, for example `-v "/path with spaces:/data"`; nothing is evaluated) and appended to the container run command:

| Host | Value |
|---|---|
| macOS (Podman Desktop / `podman machine`) | leave unset |
| SELinux-enforcing Linux (RHEL / Fedora / CentOS Stream) | `DOCKER_RUN_EXTRA_ARGS="--security-opt label=disable"` |
| Rootless Podman on Linux | `DOCKER_RUN_EXTRA_ARGS=--add-host=host.docker.internal:host-gateway` |
| Both of the above | `DOCKER_RUN_EXTRA_ARGS="--security-opt label=disable --add-host=host.docker.internal:host-gateway"` |

- **Wrap the value in double quotes whenever it contains a space.** Without quotes the shell
  reads only the first word and the rest is silently dropped.
- `--security-opt label=disable` is preferred over adding `,z` to the mounts: `,z` relabels
  the files on the host, which would change the SELinux labels of shared binaries such as
  `/usr/local/bin/terraform`.
- **Do not set `--add-host` on macOS.** The `podman machine` VM already defines
  `host.docker.internal`, and Podman fails with
  `unable to replace "host-gateway" of host entry "host.docker.internal"`.
- On macOS, only paths shared into the `podman machine` VM can be mounted. `/tmp` is not
  shared by default, so keep `DATA_DIR` and the binary paths under your home directory.

## Usage

### Pre-flight Check (Recommended)

Before running the pipeline, verify all prerequisites are met:

```bash
# Check all prerequisites
./pre-check.sh

# Or check specific components
# ("docker" here is the name of the container-engine check, not the CLI:
#  keep it as "docker" even when DOCKER_CLI=podman)
./pre-check.sh workdir   # Working directory path only
./pre-check.sh docker    # Container engine only
./pre-check.sh env       # Environment variables only
./pre-check.sh binaries  # terraform/tfpolicy binaries only
./pre-check.sh input     # Input file only
./pre-check.sh image     # Container image only
./pre-check.sh mcp       # MCP server only
./pre-check.sh output    # Output directory only
./pre-check.sh local     # Local mode config only
./pre-check.sh external  # External mode config only
./pre-check.sh api       # API credentials only

# JSON output for automation
./pre-check.sh --json
./pre-check.sh mcp --json
```

Note: `pre-check.sh` automatically detects and uses the available Python interpreter (`python3` or `python`).

The pre-flight check will verify:
- 🟢 **docker**: The container engine set by `DOCKER_CLI` is running
- 🟢 **env**: Environment variables are properly configured
- 🟢 **binaries**: terraform and tfpolicy binaries are available and executable
- 🟢 **input**: Input files exist
- 🟢 **image**: Container image is available
- 🟢 **mcp**: MCP server is accessible at localhost:8500
- 🟢 **output**: Output directory is empty (ready for pipeline)
- 🟢 **local**: Local mode — `EXTERNAL_REPO_DIR` is not set, `INPUT_DIR`/`INPUT_FILE`/`OUTPUT_DIR` are present
- 🟢 **external**: External mode — `EXTERNAL_REPO_DIR` is set and the directory exists
- 🟢 **workdir**: Working directory path has no unsafe characters
- 🟢 **api**: API credentials are valid (tested via lightweight ping)

If any issues are found, the tool will provide clear error messages with 🔴 status and suggestions for fixing them.

**Mode-based check behaviour** — When running `./pre-check.sh` (all checks), only the check for your configured mode is shown: the `external` check if `EXTERNAL_REPO_DIR` is set, otherwise the `local` check. You can still run `./pre-check.sh local` or `./pre-check.sh external` explicitly; an explicit check for the mode you are not using reports 🔴.

### Primary Use Case: External Repository Integration

To convert Sentinel or OPA (`.rego`) policy libraries from an external repository (e.g., HashiCorp's CIS Policy Set for AWS Terraform):

Example repository: https://github.com/hashicorp/policy-library-CIS-Policy-Set-for-AWS-Terraform/tree/main/policies/cloudtrail

**Step 1: Download or clone the external repository**

```bash
# Option A: Download and extract
curl -L https://github.com/hashicorp/policy-library-CIS-Policy-Set-for-AWS-Terraform/archive/refs/heads/main.zip -o repo.zip
unzip repo.zip -d /tmp

# Option B: Clone the repository
git clone https://github.com/hashicorp/policy-library-CIS-Policy-Set-for-AWS-Terraform.git /tmp/sentinel-repo
```

**Step 2: Set the external repository path in `.env`**

```bash
EXTERNAL_REPO_DIR=/tmp/policy-library-CIS-Policy-Set-for-AWS-Terraform-main/policies/cloudtrail
```

**Step 3: Run the pipeline**

```bash
./run.sh  # Auto-detects external mode when EXTERNAL_REPO_DIR is set
```

Or explicitly specify external mode:
```bash
./run.sh external  # Force external mode
```

The script automatically:
- Detects `EXTERNAL_REPO_DIR` is set and runs in external mode
- Extracts `.sentinel` and `.rego` files from the repository
- Creates timestamped directories (`data/input-YYYYMMDD_HHMMSS/`, `data/output-YYYYMMDD_HHMMSS/`)
- Generates policies
- Deploys results to `EXTERNAL_REPO_DIR/tfpolicy/`

Example output structure:

````
    return maps.get(res, "values.versioning.0.enabled", false)

````

**Option B: Policy File Paths**


Or explicitly specify local mode:

Output files are generated in the directory specified by `OUTPUT_DIR` in your `.env` file (default: `data/output`):

## What is in the image

The image (`docker.io/hashicorp/terraform-policy-agent`) is a Linux container (Alpine base, `linux/amd64` and `linux/arm64`) that bundles everything the agent needs except your credentials and the Terraform / TFPolicy binaries:

| Component | Details |
|---|---|
| [OpenCode](https://opencode.ai) | AI coding agent runtime (pinned version, 1.19.0 at the time of writing). The model provider (GitHub Copilot, Amazon Bedrock or LiteLLM) is configured from your `.env` via `{env:VAR}` placeholders in the bundled `opencode.json`. |
| Pipeline skills | The skills for each stage (extraction, requirement, generation, summary, validation fixtures) and the shared TFPolicy authoring skills, under `/workspace/.opencode/skills` and `/skills`. |
| Local MCP server | A small Python MCP server (`my-python-tools`, on port 8300 inside the container) used by the pipeline for helper tools. |
| External MCP server | The pipeline connects to the `terraform-mcp-server` you run on the host (`host.docker.internal:8500`; see [Required MCP Server](#required-mcp-server)). It is **not** part of the image. |
| Terraform provider cache | The AWS provider (`~> 6.0`) is pre-cached so schema validation works offline. |
| Terraform and TFPolicy binaries | **Not** bundled. You mount your own Linux binaries at runtime (see [Required Binaries](#2-prerequisites)). |

## Pipeline Stages

The pipeline runs stages 0 to 3 by default, plus an optional Stage 4. Each stage must complete before the next begins.

| Stage | What it does | Output |
|---|---|---|
| **Stage 0** | Authenticates with the LLM provider and extracts policy goals from `policy_goal.txt` | `data/output/goals/` |
| **Stage 1** | Generates detailed requirements for each policy goal (runs in parallel) | `data/output/PolicyName/requirement.txt` |
| **Stage 2** | Generates policy files and tests for each requirement (runs in parallel) | `data/output/PolicyName/*.hcl`, `*.tf` |
| **Stage 3** | Creates a consolidated summary report | `data/output/summary.md` |
| **Stage 4** (optional) | Generates validation fixtures: a passing and a failing Terraform configuration per policy, based on the policy's test scenarios (`gwt.json`). Runs after Stage 2 for policies that succeeded. | `data/output/PolicyName/pass_config.tf`, `fail_config.tf` |

**Stage 4 is disabled by default.** Enable it by setting `ENABLE_STAGE4=true` in `.env`. Its timeout (per policy) is `STAGE4_TIMEOUT` (default 300 seconds). A Stage 4 failure does not fail the run.

> **If the pipeline fails at Stage 0**, the most likely cause is an invalid or expired API key / token. First, run `./pre-check.sh api` to confirm whether your credentials are valid. If the check fails, re-acquire your tokens and update `.env`. See [Troubleshooting](./TROUBLESHOOTING.md) for fixes.

## Data and Privacy

Terraform Policy Agent runs an AI coding agent inside a container. Be aware of what leaves your machine:

- **Your policy content is sent to the model provider you configure.** The Sentinel policy source, the generated goals and requirements, and the prompts built from them are sent to GitHub Copilot, Amazon Bedrock, or your LiteLLM endpoint (depending on `AUTH_PROVIDER`). Do not use a provider you are not permitted to share this content with.
- **The Terraform MCP server queries the Terraform registry.** The agent uses `terraform-mcp-server` to look up provider and resource information. These lookups go to the public Terraform registry.
- **Everything else stays local.** Input policies, outputs, logs and checkpoints are written to your local `data/` (or `output-*`) directories. The tool itself does not upload them anywhere.
- **Generated files and logs may contain your policy content.** Review them before sharing them in issues or screenshots.

## Credentials and Token Handling

- Keep credentials (`GITHUB_COPILOT_ACCESS_TOKEN`, `GITHUB_COPILOT_REFRESH_TOKEN`, `MODEL_API_KEY`) only in your local `.env` file or shell environment. **Never commit `.env`**; it is listed in `.gitignore`.
- Use a dedicated, least-privilege token or API key for this tool, and revoke or rotate it when you no longer need it, or if it may have been exposed.
- The run scripts pass credentials to the container by variable name (`-e VAR`), not by value, so they are not printed by `--dryrun` and do not appear in the process list.
- Redact tokens, API keys, hostnames and personal paths from logs and screenshots before sharing them. To report a vulnerability, see [SECURITY.md](SECURITY.md).

## Advanced Usage

### Run Specific Steps (Local Mode)

```bash
./run.sh local --step 0
./run.sh local --step 1 --goal-file goal-001.txt
./run.sh local --step 2 --policy-dir CloudFront_Associated_WAF
./run.sh local --step 3
```

### Run Specific Phases (External Mode)

```bash
./run.sh external --phase preprocess    # Extract only
./run.sh external --phase generate      # Generate only
./run.sh external --phase postprocess   # Deploy only
```

### Resume from Checkpoint

Interrupted runs save progress to `.checkpoint` in `DATA_DIR`. Use `--resume` to pick up from the last completed stage without re-running earlier steps:

```bash
./run.sh --resume local      # local mode
./run.sh --resume external   # external mode
```

### Skip Confirmation Prompts (No-Confirm Mode)

Pass `--no-confirm` to suppress all interactive yes/no prompts and let the pipeline run unattended:

```bash
./run.sh --no-confirm local
./run.sh --no-confirm external
```

Both flags can be combined:

```bash
./run.sh --no-confirm --resume local
./run.sh --no-confirm --resume external
```

### Help

```bash
./run.sh --help
./run.sh local --help
./run.sh external --help
```

### Pipeline Fails
- Check `data/input/policy_goal.txt` exists and is properly formatted
- Verify binary paths in `.env` are correct
- Check logs in `data/output/stage*.log`
